OPFS vs IndexedDB: a benchmark you can run yourself

For heavy lifting in the browser, such as offline data, large datasets or files, you have two real options: IndexedDB and the Origin Private File System (OPFS). Most published benchmarks come from vendors. I ran my own on an M1 MacBook Air in Chrome, Firefox and Safari, and you can run the same test in your browser, right on this page.

By Alexandru Cobuz · Senior full-stack engineer · 10 min read · Updated 26 Nov 2026

The short answer

  • Saving a large dataset in one go: OPFS wins. It was 5–10× faster than IndexedDB in Chrome, Firefox and Safari.
  • Changing one record: IndexedDB wins by far. It took under 5 ms, while rewriting a 50 MB OPFS file took 134–320 ms.
  • Reading everything back: it depends on the browser. OPFS was 3× faster in Chrome, slightly faster in Firefox, and level with IndexedDB in Safari.
  • OPFS can match IndexedDB on small updates, but only if you store records at fixed positions in the file instead of as one big JSON blob.

The difference in data model explains almost every result below. IndexedDB knows where each record lives, so it can change one without touching the rest. OPFS only knows bytes. If you save your data as one JSON file, OPFS has no idea where record 5 is, so a change means reading, parsing and rewriting the whole file.

Results on an M1 MacBook Air

I ran an extended version of the benchmark on my own MacBook Air (M1, 8 GB) in Chrome, Firefox and Safari. Each test ran five times after a warm-up run, and the charts show the median. Everything ran inside a Web Worker, so every storage type had the same conditions.

To keep it fair, the records hold random text, which can't be compressed, and the time to convert data to and from JSON counts for OPFS too. IndexedDB does that conversion itself, so leaving it out for OPFS would flatter OPFS.

Saving 50 MB: OPFS is 5–10× faster

IndexedDB stores each record separately and maintains its index as it goes. OPFS just writes one long run of bytes. For "save everything now", like an export, a backup or a downloaded dataset, OPFS is clearly faster in every browser.

Changing one record: IndexedDB is up to 600× faster

This is the result that should decide most projects. If your app changes data often, such as a to-do list, a form draft or a sync queue, a single OPFS file has to be rewritten on every change, and the cost grows with the size of the file. IndexedDB only touches the one record, so the size of everything else doesn't matter.

OPFS isn't stuck with this. When each record has a fixed size and a known position in the file, a change is one small write at that position. That took about 1 ms in every browser, as fast as IndexedDB. The code is in the Web Worker section below.

Some limits, so you read these numbers the right way:

  • It's one machine. A phone, or a laptop with a slower disk, will give different numbers, so the ratios matter more than the milliseconds.
  • Chrome ran in headless mode, without a visible window. Firefox and Safari ran normally.
  • Firefox and Safari round timings to the nearest millisecond for privacy reasons, so anything under 5 ms in those columns is approximate.

Which one should you use?

Your dataUseWhy
Records you look up, filter or update: offline app data, caches, sync queuesIndexedDBIndexes, and single-record changes in milliseconds
Large files you save and load whole: media, exports, downloaded datasetsOPFS5–10× faster to save, no record overhead
Data you mostly append to: logs, recordings, event streamsOPFSAppend at the end of the file with a sync access handle
A real database in the browser (SQLite compiled to WebAssembly)OPFSSQLite stores fixed-size pages at known positions, which is exactly what OPFS does well
Both: structured records plus big attachmentsBothRecords and metadata in IndexedDB, file contents in OPFS, linked by an ID

If you're unsure, start with IndexedDB. It's the safer default for app data, and you can move the large binary parts to OPFS later, when you have numbers that show it's worth it.

Going with OPFS? Plan for your app being open in two tabs: the second tab can't open a file the first one holds. See OPFS in multiple tabs: fixing NoModificationAllowedError.

Practical rules

  • Batch writes into one transaction. Saving 1,000 records with one transaction each took 478 ms in Safari, against 34 ms in a single transaction: 14× slower. Chrome and Firefox were about 3× slower. Many tiny transactions are the most common IndexedDB slowdown.
  • Don't keep changing data in one big OPFS file. Every change rewrites the whole file. Use fixed-size slots, several smaller files, or IndexedDB.
  • Don't count on durability: "relaxed". It's meant to speed up IndexedDB writes by not waiting for the disk, but it made no measurable difference on the M1 in any browser. Measure it in your own app before relying on it.
  • Split big data into chunks instead of one giant record, so updates only rewrite what changed.
  • Prefer ArrayBuffers for binary data in IndexedDB. Blob storage has had browser-specific problems, notably on older Safari versions.
  • Ask for persistence with navigator.storage.persist() when losing the data would hurt.
  • Test in every target browser. Reading 50 MB from OPFS was 3× faster than IndexedDB in Chrome, but no faster at all in Safari.

FAQ

Is OPFS faster than IndexedDB?

For saving large data in one go, yes. On an M1 MacBook Air, OPFS saved 50 MB 5–10× faster than IndexedDB in Chrome, Firefox and Safari. For changing a single record, no: IndexedDB took under 5 ms, while rewriting a 50 MB OPFS file took 134–320 ms. Reading everything back was 3× faster with OPFS in Chrome and the same speed in Safari.

When should I use IndexedDB instead of OPFS?

Use IndexedDB for structured records you need to look up, filter, index or update often, such as offline app data, caches and sync queues. Use OPFS for files and large binary data you read and write as a whole or in chunks, like media, exports, logs or a SQLite database file.

Is OPFS good for data that changes often?

Only if you design the file layout. Rewriting one big JSON file for every change is slow, and gets slower as the file grows. Storing records in fixed-size slots at known positions, written with a sync access handle in a Web Worker, made single-record changes take about 1 ms, as fast as IndexedDB. SQLite on OPFS works the same way, with fixed-size pages.

Why is my IndexedDB so slow?

Usually because every write has its own transaction. In Safari on an M1, saving 1,000 records in separate transactions took 478 ms, against 34 ms in one transaction. Chrome and Firefox were about 3× slower. Batch writes into one transaction, and do heavy work in a Web Worker.

Do OPFS and IndexedDB work in Web Workers?

Yes. Both are available in workers, which is where heavy work belongs so the UI stays responsive. OPFS's fastest API, createSyncAccessHandle, is only available inside dedicated Web Workers.

How much can I store in IndexedDB or OPFS?

Both share the same per-origin quota, which depends on the browser and free disk space and is usually far larger than localStorage. Check the current estimate with navigator.storage.estimate(), and request persistence with navigator.storage.persist() if the data shouldn't be evicted.

Does this benchmark send my data anywhere?

No. It generates random dummy data, saves and reads it locally in your browser, then deletes it. Nothing leaves your device.
