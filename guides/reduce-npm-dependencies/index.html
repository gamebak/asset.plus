Less code = more: how to reduce npm dependencies

Every package you install is code you didn't write, didn't review and now have to trust. With AI assistants adding packages faster than ever, keeping dependencies lean is one of the cheapest security and performance wins available.

By Alexandru Cobuz · Senior full-stack engineer · 7 min read

Why this matters more in the AI era

A typical modern app pulls in hundreds of transitive packages. Each one can be abandoned, broken by an upgrade, or hijacked in a supply-chain attack. AI coding assistants make this worse: they add a package for a five-line task without hesitation.

My rule, long before AI: zero dependencies is the aspiration, not the constraint. Every package has to earn its place.

Step 1: See what you actually have

Check the size of anything new before adding it. Tools like Bundlephobia (browser) and Packagephobia (install size) make the cost visible.

Step 3: Using one function from a big library? Port it

A common pattern: a project installs a whole utility library and uses one or two functions from it. In that case, the better move is often to port just what you use into your own code. You get one less package to update and audit, and code you actually understand.

If the answer is "just debounce", that's ten lines:

  • 1
    Check the license. MIT, BSD and Apache allow copying, but you must keep the copyright and license notice. A comment with the source and license is enough.
  • 2
    Port only what you need. You don't need every option and edge case the library supports, only the behaviour your app relies on.
  • 3
    Add tests for that behaviour before removing the package, so the swap is provably safe.
  • 4
    Then uninstall and check the bundle size and lockfile shrink.

When not to port: security-sensitive code (cryptography, authentication, parsers of untrusted input) and anything that changes often. There you want the maintainers' fixes, not a frozen copy.

Step 4: Put guardrails in place

  • Commit the lockfile and install with npm ci in CI, so builds use exactly what you reviewed.
  • Review new dependencies in pull requests like code: who maintains it, how big is it, what does it pull in?
  • Automate updates with Renovate or Dependabot, in small batches you can actually review.
  • Be careful with install scripts: they run arbitrary code on your machine and in CI.

When a dependency is worth it

Lean doesn't mean reinventing everything. Cryptography, parsers, database drivers and complex domains (dates across time zones, PDFs, payments) are exactly where a well-maintained library beats home-made code. The goal is intentional dependencies, not zero at any cost.

Smaller bundles also mean faster serverless cold starts. More on that in the AWS Lambda cost guide.

FAQ

Why reduce npm dependencies?

Fewer dependencies mean a smaller attack surface for supply-chain attacks, fewer breaking upgrades, faster installs and builds, smaller bundles and faster cold starts on serverless platforms like AWS Lambda.

How do I find unused dependencies?

Start with npm ls --all to see the full tree and npm explain <package> to see why something is installed. A one-off run of a tool such as depcheck flags packages your code never imports.

Which packages can be replaced with native Node.js APIs?

Common ones: node-fetch and axios (global fetch), uuid (crypto.randomUUID), dotenv (node --env-file), nodemon (node --watch), rimraf (fs.rm with recursive), and many lodash helpers (modern array and object methods, structuredClone).

Should I copy a function from an npm package into my project?

If you only use one or two small functions from a large library, porting them into your own codebase is often the better trade: one less dependency to update and audit, and code you fully understand. Check the license first (MIT and similar licenses require keeping the copyright notice), add tests, and keep a comment pointing to the original. Don't do it for security-sensitive code like cryptography or parsers, where you want the maintainers' fixes.

Does AI-generated code add more dependencies?

Often, yes. Assistants tend to reach for a package for small tasks the platform already handles, and occasionally suggest packages that don't exist, which attackers can register. Review every new dependency in pull requests, whoever wrote the code.
