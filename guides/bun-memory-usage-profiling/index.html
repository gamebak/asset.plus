Bun memory usage: find leaks and slow code with profiling

"Bun uses too much memory" can mean a leak, a large cache, native memory or nothing wrong at all. This guide shows how to tell them apart with object counts, heap snapshots and CPU flamegraphs, plus the practices that keep memory stable in production.

By Alexandru Cobuz · Senior full-stack engineer · 7 min read

The short answer

  • Memory too high? Compare RSS with the JS heap first. They point to different causes.
  • Memory keeps climbing? Force a garbage collection, compare object counts, then compare two heap snapshots.
  • CPU too high or responses slow? Record a CPU profile and read it as a flamegraph.
  • Whatever you find: change one thing and repeat the same test.

RSS, heap and native memory

“Bun uses 300 MB” doesn't say much on its own. Bun has two heaps: one for JavaScript objects (JavaScriptCore), and one for everything else (mimalloc).

MetricWhat it tells youWhere to read it
RSSMemory the process holds in RAMprocess.memoryUsage()
JS heapMemory tracked by JavaScriptCoreheapStats()
BuffersBinary data such as Uint8Arrayexternal in process.memoryUsage()
Native heapBun's own allocationsBun.unsafe.mimallocDump()

Don't add these up, because they overlap. In a test on Bun 1.4.4, holding 60 MB of Uint8Array data showed up in both external and heapSize, while arrayBuffers stayed at 0.

How to read them together:

  • RSS and object counts both climb: your code is probably holding on to objects. Start with heap snapshots.
  • RSS climbs but the heap and counts don't: suspect native memory, such as a native addon or the runtime itself. Check the mimalloc output and try the latest Bun version.
  • RSS jumps, then stays flat: often normal. Freed memory isn't always returned to the operating system right away.
  • RSS looks smaller than the heap: possible when the system compresses or swaps memory, for example on macOS. Don't compare a Mac number with a Linux one.

CPU flamegraphs

A CPU profile shows which functions are using your time. Bun writes one when the process exits:

Open the .cpuprofile in the Performance tab of Chrome DevTools with “Load profile”, or in VS Code.

  • Look for wide blocks, not tall stacks. Width is cost; depth is only how many calls led there.
  • Compare self time and total time. High self time means the function itself is expensive. High total time can come from what it calls.
  • Profile under realistic load. An idle server's profile tells you nothing about a busy one.
  • A slow endpoint with an empty CPU profile is probably waiting on a database or network, so optimize that instead.

Heap snapshots

A heap snapshot shows what is in memory and what is keeping it there. You can write one on exit, or from a running process:

  • Start with DEBUG_MEMORY=1, warm the app up, and take snapshot A.
  • Run the load, stop it, let the app settle, and take snapshot B.
  • Load both in the Memory tab of Chrome DevTools. If the file ends in .heapprofile, rename it to .heapsnapshot.
  • Select B, switch from Summary to Comparison, and sort by Delta.
  • Open a growing type and follow its Retainers. That chain is the code keeping it alive.

Treat snapshots as secrets. They contain your app's real data, including tokens and personal details. Taking one also pauses the app and needs extra memory, so avoid it on an instance that is already near its limit.

Common causes of growing memory

  • Unbounded caches: a Map that only ever grows. Add a size limit or an expiry.
  • Listeners never removed: everything they reference stays alive. Use once or remove them.
  • Forgotten timers: clear every setInterval when its owner goes away.
  • Closures over large objects: keep only the fields you need.
  • Promises that never settle: put a timeout on outgoing calls, for example AbortSignal.timeout(5000).
  • Whole files or responses in memory: stream large data, and don't start unlimited work at once.

Common practices for production

  • Set a memory limit on the container and alert before you reach it.
  • Chart RSS over days, next to request rate and deploys. One reading can't show a trend.
  • Load test for hours before migrating. Short benchmarks miss slow leaks.
  • Test --smol on small instances. It collects garbage more often to use less memory, which can cost CPU.
  • Pin the Bun version and repeat your memory test when you upgrade.
  • Restarting on a schedule is a stopgap. It buys time, but keep looking for the cause.

FAQ

How do I check Bun memory usage?

Use process.memoryUsage() for RSS and heapStats() from bun:jsc for the JavaScript heap. Run Bun.gc(true) first when diagnosing, so you compare live objects instead of garbage, and look at the trend over several rounds of load.

Does Bun use less memory than Node.js?

It depends on the workload, the versions and the operating system, and published results disagree. Run your own app on both runtimes with the same load for several hours and compare RSS over time.

How do I create a flamegraph in Bun?

Run your app with bun --cpu-prof, send it realistic load and exit cleanly. Bun writes a .cpuprofile file that you can open in the Performance tab of Chrome DevTools or in VS Code.

Why did bun --cpu-prof not create a file?

Bun writes the profile when the process exits. In a test on Bun 1.4.4, stopping a server with Ctrl+C or SIGTERM wrote nothing until the app handled the signal and called process.exit().

How do I know if my Bun app has a memory leak?

Apply the same load in rounds, force a garbage collection after each one, and compare. If memory or the count of one object type keeps rising every round and never levels off, it's probably a leak. Compare two heap snapshots to find what is holding on to it.
