The iOS Safari 60fps limit: making web apps feel native

I always hated that the web apps I coded didn't feel like native apps. The layout could be perfect and the code fast, and something was still off the moment you dragged it with a finger. A big part of it was a limit I couldn't code around: on iPhone, Safari updates web pages at 60fps, even on a 120Hz screen.

By Alexandru Cobuz · Senior full-stack engineer · 6 min read

A limit only web developers have

If you build native, a ProMotion iPhone gives you up to 120 frames a second. If you're strictly a web developer, you get half, on the same phone and the same screen. You can remove frameworks, shrink bundles and optimise every function, and you still hit the same wall. That's what made it a pain: it wasn't my code, so I couldn't fix it.

WebKit has two reasons: higher frame rates use more power, and some pages misbehave when their callbacks run faster than 60 times a second. Fair reasons, but the choice isn't left to the developer. There is a Safari setting, “Prefer Page Rendering Updates near 60fps”, but you can't ask your users to dig through feature flags.

What changed

Then I read Rida F'kih's Bypassing iOS Safari’s 60 FPS Limit. It shows a way around the limit with standard web APIs. This article is a follow-up: the same idea in simpler terms, with code you can copy. The discovery and every measurement mentioned here are Rida's, so read the original for live demos and for how it was found.

Rida's recording of an iPhone 18 Pro averaged 118fps during a drag, against 60fps with normal pointer events.

The idea in simple terms

There are two limits, and you need to get past both:

The limitThe way around
OutputWhat the page draws appears at 60fpsDraw on an OffscreenCanvas in a worker
InputTouch events on a normal page arrive at 60HzPut an invisible scrolling area under the finger

Think of the page as a bus that leaves 60 times a second. Everything you change in the DOM waits for the next bus. A canvas handed to a worker doesn't: in WebKit its frames can be shown without waiting for the page.

Scrolling was never on that bus. Safari moves scrolled content outside your JavaScript, which is why scrolling feels native on even a slow website. So we let the finger scroll something invisible, and use that movement for our own interface.

When I would use it

  • Good fit: drawing tools, games, maps, sliders, dials, and one or two gestures people use all day.
  • Not needed: normal scrolling, and simple movement that CSS animations already handle.
  • Bad fit: a whole app. Text in a canvas isn't selectable, searchable or readable by a screen reader unless you build that separately.
  • Draw only when something changes. More frames use more battery, so nothing should run while the screen is idle.
  • Keep a plain version. If transferControlToOffscreen is missing, fall back to a normal canvas or to the DOM.
  • Expect it to change. It depends on how WebKit works today, and Apple could make those frames wait for the page again. Rida wouldn't rebuild a whole application around it, and neither would I.

Treat the code as a starting point and test it on real ProMotion devices. Low Power Mode and Limit Frame Rate (Settings, Accessibility, Motion) both lower the frame rate, and the iOS simulator won't show you 120Hz.

Will the web ever feel native?

I don't think frame rate is the only difference, but it's the one you feel without knowing why. For years the answer was “build a native app”. Now a small part of the interface, the part under the finger, can run at the speed of the screen, with nothing but web code. The best outcome would be for Apple to lift the limit and make this article useless.

FAQ

Why is Safari limited to 60fps on iPhone?

WebKit limits page updates to about 60 per second to save power and because some pages misbehave when animation callbacks run faster. The limit applies even on 120Hz ProMotion screens.

Can a web app run at 120fps on iOS?

Parts of it can. Scrolling isn't held to the page's 60fps, and a canvas drawn by a worker through OffscreenCanvas can be shown faster than the page. Normal DOM updates and requestAnimationFrame on the page stay at about 60.

Does requestAnimationFrame run at 120Hz in Safari on iPhone?

Not by default. It runs at about 60 per second unless the user turns off the Prefer Page Rendering Updates near 60fps flag in Safari's settings.

Does OffscreenCanvas bypass the 60fps limit?

In current WebKit on iOS, yes, according to Rida F'kih's tests. Frames from an OffscreenCanvas don't wait for the page's next rendering update. It isn't a guaranteed behaviour, so a future Safari version could change it.

Is it safe to use in production?

Use it as an enhancement for one interaction, with a fallback, keyboard access and testing on real devices. Don't make the whole app depend on it.
